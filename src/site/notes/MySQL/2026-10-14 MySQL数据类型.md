## 1.1 数据类型分类与约束思维

### 1.1.1 数据类型分类

MySQL 数据类型可以按用途分为以下几类：

| 类型类别 | 常见类型 | 主要用途 |
| --- | --- | --- |
| 数值类型 | `TINYINT`、`INT`、`BIT`、`FLOAT`、`DECIMAL` | 保存整数、位字段、浮点数和定点数 |
| 字符串类型 | `CHAR`、`VARCHAR` | 保存固定长度或可变长度文本 |
| 日期时间类型 | `DATE`、`DATETIME`、`TIMESTAMP` | 保存日期、日期时间或时间戳 |
| 枚举与集合类型 | `ENUM`、`SET` | 保存单选项或可多选的集合 |

在表中建立属性列时，基本写法是“列名在前，数据类型在后”，例如：

```sql
CREATE TABLE 表名 (
    列名 数据类型
);
```

### 1.1.2 数据类型为什么也是一种约束

如果向 MySQL 的数据类型中插入不合法的数据，MySQL 一般会直接拦截操作，或者根据当前 SQL 模式给出警告。这与某些编程语言会悄悄接受越界值的做法不同。

反过来看，只要数据已经成功插入 MySQL，那么它通常就是符合列类型限制的。因此，数据类型不仅说明“这一列存什么”，也约束“这一列能存什么”：

- 数据类型限制取值范围、长度和精度。
- 类型约束会倒逼程序员在写入前检查和构造合法数据。
- 数据库因此可以保证数据是可预期的、完整的，尽量避免截断、越界或错误数据进入表中。
- MySQL 可能对 SQL 语句进行等价改写或规范化，但不会因此放宽数据类型本身的限制。

可以把数据类型理解成数据库写给使用者的一组规则：使用者负责正确写入，数据库负责守住边界。

### 1.1.3 本篇阅读路径

学习一种数据类型时，可以依次关注四个问题：

1. 语法是什么，括号中的参数分别表示什么？
2. 取值范围、长度、精度和占用空间是多少？
3. 插入边界值时会发生什么？
4. 在实际场景中应该选择哪种类型？

## 1.2 数值类型

### 1.2.1 TINYINT：整数类型入门

`TINYINT` 是最小的常用整数类型。可以先用它观察 MySQL 如何检查整数范围。

```sql
CREATE TABLE tt1 (
    num TINYINT
);
```

创建后可以查看表结构：

![[查看tinyint类型.png]]

`DESC` 和 `SHOW CREATE TABLE` 可能把类型显示为 `tinyint(4)`。这里的 `4` 属于显示宽度相关信息，并不表示只能保存 4 位数字，也不改变 `TINYINT` 的实际取值范围。

正常的边界值可以插入：

![[往tinyint里面插入一些数据.png]]

```sql
INSERT INTO t1 VALUES('-128');
INSERT INTO t1 VALUES('127');
INSERT INTO t1 VALUES('-1');
INSERT INTO t1 VALUES('1');

SELECT * FROM t1;
```

示例结果：

```text
+-------+
| num   |
+-------+
| -128  |
|  127  |
|   -1  |
|    1  |
+-------+
4 rows in set (0.01 sec)
```

越界插入会被拒绝：

```sql
CREATE TABLE tt1 (
    num TINYINT
);

INSERT INTO tt1 VALUES(1);
INSERT INTO tt1 VALUES(128);
```

最后一条语句报错：

```text
ERROR 1264 (22003): Out of range value for column 'num' at row 1
```

随后查询表时，表中仍然只有合法的数据：

```text
+------+
| num  |
+------+
|    1 |
+------+
1 row in set (0.00 sec)
```

### 1.2.2 有符号与无符号

MySQL 整数类型默认是有符号的，可以通过 `UNSIGNED` 声明无符号整数。

`TINYINT` 的取值范围如下：

| 类型 | 取值范围 |
| --- | --- |
| `TINYINT` | -128 到 127 |
| `TINYINT UNSIGNED` | 0 到 255 |

无符号示例：

```sql
CREATE TABLE tt2 (
    num TINYINT UNSIGNED
);

INSERT INTO tt2 VALUES(-1);
```

由于无符号类型不能保存负数，该语句报错：

```text
ERROR 1264 (22003): Out of range value for column 'num' at row 1
```

而最大值可以正常插入：

```sql
INSERT INTO tt2 VALUES(255);
SELECT * FROM tt2;
```

```text
+------+
| num  |
+------+
|  255 |
+------+
1 row in set (0.00 sec)
```

选择建议：

- 默认优先使用有符号整数。
- 不要仅仅为了扩大正数范围就习惯性使用 `UNSIGNED`。如果一个 `INT` 可能出现 `INT UNSIGNED` 仍放不下的数据，更稳妥的做法是直接提升为 `BIGINT`。
- 设计表时应根据真实业务范围选择类型，不要总用最大整数类型。

### 1.2.3 BIT：位字段类型

基本语法：

```sql
BIT[(M)]
```

- `M` 表示每个值使用的二进制位数。
- `M` 的范围是 1 到 64。
- 省略 `M` 时默认为 `BIT(1)`。
- 适合保存布尔值、状态位或只需少量二进制位的字段。

示例：

```sql
CREATE TABLE tt4 (
    id INT,
    a BIT(8)
);

INSERT INTO tt4 VALUES(10, 10);
SELECT * FROM tt4;
```

直接查询时，`BIT` 字段可能不可见或显示为空白：

```text
+------+------+
| id   | a    |
+------+------+
|   10 |      |
+------+------+
1 row in set (0.00 sec)
```

原因是 `BIT` 的显示与二进制值对应的字符有关。控制字符无法正常显示，所以终端中可能只看到空白。

再插入一个值 `65`：

```sql
INSERT INTO tt4 VALUES(65, 65);
SELECT * FROM tt4;
```

```text
+------+------+
| id   | a    |
+------+------+
|   10 |      |
|   65 | A    |
+------+------+
2 rows in set (0.00 sec)
```

在 ASCII 中，十进制 `65` 对应字符 `A`，因此结果中显示出 `A`。这说明 `BIT` 的值仍然存在，只是默认显示方式不一定直观。

如果只想保存 `0` 或 `1`，可以定义 `BIT(1)`：

```sql
CREATE TABLE tt5 (
    gender BIT(1)
);

INSERT INTO tt5 VALUES(0);
INSERT INTO tt5 VALUES(1);
INSERT INTO tt5 VALUES(2);
```

插入 `2` 时已经超出 `BIT(1)` 能表示的范围：

```text
ERROR 1406 (22001): Data too long for column 'gender' at row 1
```

课堂中的另一个例子是保存在线状态：

```sql
INSERT INTO t3 (id, online) VALUES (123, 0);
INSERT INTO t3 (id, online) VALUES (124, 1);
INSERT INTO t3 (id, online) VALUES (124, 3);
```

前两条插入成功，第三条超过 `BIT(1)` 的范围：

![[bit不可见.png]]

直接查询 `SELECT * FROM t3` 时仍可能看不到位值。可以通过十六进制形式观察：

```sql
SELECT id, HEX(online) FROM t3;
```

![[bit使用十进制查询可见.png]]

结果中的 `0` 和 `1` 证明位字段实际保存了数据。也可以把字段改成更多位，例如：

```sql
ALTER TABLE t3 MODIFY online BIT(10);
```

![[将t3改为10个比特位.png]]

### 1.2.4 FLOAT：单精度浮点数

基本语法：

```sql
FLOAT[(M, D)] [UNSIGNED]
```

- `M` 表示显示长度，也就是整数部分与小数部分合计允许的位数。
- `D` 表示小数位数。
- `FLOAT` 通常占用 4 个字节。
- MySQL 保存 `FLOAT` 时可能进行四舍五入。
- `FLOAT` 的精度大约为 7 位有效数字。

创建表：

```sql
CREATE TABLE IF NOT EXISTS t5 (
    id INT,
    salary FLOAT(4, 2)
);
```

![[创建小数类型的数据.png]]

`FLOAT(4, 2)` 表示总位数为 4，其中小数占 2 位，整数部分最多占 2 位。因此有符号范围是：

```text
-99.99 到 99.99
```

按照同样的规则，`FLOAT(6, 3)` 的范围是：

```text
-999.999 到 999.999
```

插入示例：

```sql
INSERT INTO t5 (id, salary) VALUES (1, 99.99);
INSERT INTO t5 (id, salary) VALUES (1, -99.99);
SELECT * FROM t5;
```

![[向浮点数中插入一些数据.png]]

PDF 中的越界与舍入示例：

```sql
CREATE TABLE tt6 (
    id INT,
    salary FLOAT(4, 2)
);

INSERT INTO tt6 VALUES(100, -99.99);
INSERT INTO tt6 VALUES(101, -99.991);

SELECT * FROM tt6;
```

```text
+------+--------+
| id   | salary |
+------+--------+
| 100  | -99.99 |
| 101  | -99.99 |
+------+--------+
2 rows in set (0.00 sec)
```

`-99.991` 多出的小数位在合法范围内被舍入，并不是无条件把所有超长数据直接拦截。

无符号浮点数：

```sql
CREATE TABLE IF NOT EXISTS t6 (
    id INT,
    salary FLOAT(4, 2) UNSIGNED
);
```

![[无符号浮点数.png]]

此时范围为 `0 到 99.99`。如果插入负数，MySQL 可能给出警告：

```sql
INSERT INTO tt7 VALUES(100, -0.1);
SHOW WARNINGS;
```

```text
+---------+------+-------------------------------------------------+
| Level   | Code | Message                                         |
+---------+------+-------------------------------------------------+
| Warning | 1264 | Out of range value for column 'salary' at row 1 |
+---------+------+-------------------------------------------------+
1 row in set (0.00 sec)
```

因此不能把 `UNSIGNED` 只理解为“显示为正数”。它首先改变了列允许的取值范围。

课堂体会：

- 浮点数的局部处理会遵循四舍五入，但舍入结果仍必须落在合法范围内。
- 浮点数在存储和运算时可能产生精度损失。
- 如果业务需要精确表示金额等高精度小数，不能简单依赖 `FLOAT`。

### 1.2.5 DECIMAL：定点数

基本语法：

```sql
DECIMAL(M, D) [UNSIGNED]
```

- `M` 是定点数的总位数。
- `D` 是小数点后的位数。
- 省略 `D` 时默认为 0。
- 省略 `M` 时默认为 10。
- `M` 的最大值为 65。
- `D` 的最大值为 30。

创建示例：

```sql
CREATE TABLE IF NOT EXISTS t7 (
    f1 FLOAT(10, 8),
    f2 DECIMAL(4, 2)
);
```

![[创建数据类型decismal.png]]

范围为：

| 类型 | 范围 |
| --- | --- |
| `DECIMAL(5, 2)` | -999.99 到 999.99 |
| `DECIMAL(5, 2) UNSIGNED` | 0 到 999.99 |
| `DECIMAL(4, 2)` | -99.99 到 99.99 |

`DECIMAL(4, 2)` 可以保存 `99.99` 和 `-99.99`，但 `99.999` 越界。虽然小数位看起来可以被舍入为 `100.00`，舍入后的结果已经超过 `DECIMAL(4, 2)` 的整数部分容量，所以仍然会报错。

和 `FLOAT` 一样，`DECIMAL` 在合法范围内也可能对多余的小数位做舍入，并支持 `UNSIGNED`。

### 1.2.6 FLOAT 与 DECIMAL 的精度对比

两者的语法相似，但存储方式和精度不同。PDF 中的对比实验：

```sql
CREATE TABLE tt8 (
    id INT,
    salary FLOAT(10, 8),
    salary2 DECIMAL(10, 8)
);

INSERT INTO tt8 VALUES(100, 23.12345612, 23.12345612);
SELECT * FROM tt8;
```

结果体现了 `FLOAT` 的精度损失：

```text
+------+-------------+-------------+
| id   | salary      | salary2     |
+------+-------------+-------------+
| 100  | 23.12345695 | 23.12345612 |
+------+-------------+-------------+
1 row in set (0.00 sec)
```

课堂截图中的另一组对比：

![[对比decimal和float的区别.png]]

同样的输入 `23.11111111111`，`FLOAT(10, 8)` 保存后为 `23.11111069`，而 `DECIMAL(10, 8)` 保存为 `23.11111111`。可以看到 `DECIMAL` 更准确地保留了输入的小数。

核心区别：

| 对比项 | `FLOAT` | `DECIMAL` |
| --- | --- | --- |
| 数值表示 | 近似浮点数 | 定点数 |
| 精度 | 容易发生精度损失，通常约为 7 位有效数字 | 按 `M, D` 精确控制 |
| 适用场景 | 科学计算、允许误差的测量值 | 金额、评分、坐标等要求精确的小数 |
| 课堂结论 | 精度损失可能较大 | 高精度场景优先选择 |

### 1.2.7 数值类型选择建议

- 小整数优先考虑 `TINYINT`，普通整数考虑 `INT`，只有在范围确实不够时才使用 `BIGINT`。
- 表示真假或状态位时，可以使用 `BIT(1)`；需要同时查看多个二进制位时，再增加 `BIT(M)` 的位数。
- 对精度敏感的小数使用 `DECIMAL`。
- 对精度容忍度较高且需要浮点计算时使用 `FLOAT`。
- 使用 `UNSIGNED` 前先确认负数确实不会出现，并考虑未来取值范围是否会扩大。

## 1.3 字符串类型

### 1.3.1 CHAR：定长字符串

基本语法：

```sql
CHAR(L)
```

- 用于保存固定长度字符串。
- `L` 表示可存储的字符数，最大为 255。
- 这里的长度单位是“字符”，不是字节。
- 在 `utf8` 编码中，一个汉字通常占 3 个字节，但 `CHAR(2)` 仍然可以保存两个汉字。
- 定长字段会预留相应的空间。

示例：

```sql
CREATE TABLE IF NOT EXISTS t8 (
    id INT,
    name CHAR(2)
);
```

![[创建char类型的数据.png]]

可以插入：

```sql
INSERT INTO t8 (id, name) VALUES (1, 'A');
INSERT INTO t8 (id, name) VALUES (1, 'AB');
```

但不能放入 3 个字符：

```sql
INSERT INTO t8 (id, name) VALUES (1, 'ABC');
```

```text
ERROR 1406 (22001): Data too long for column 'name' at row 1
```

PDF 中的字符示例：

```sql
CREATE TABLE tt9 (
    id INT,
    name CHAR(2)
);

INSERT INTO tt9 VALUES(100, 'ab');
INSERT INTO tt9 VALUES(101, '中国');
SELECT * FROM tt9;
```

```text
+------+--------+
| id   | name   |
+------+--------+
| 100  | ab     |
| 101  | 中国   |
+------+--------+
2 rows in set (0.00 sec)
```

`CHAR(2)` 可以保存两个英文字母或两个汉字，但不能超过两个字符。

如果把长度声明为 256：

```sql
CREATE TABLE tt10 (
    id INT,
    name CHAR(256)
);
```

会报长度错误：

```text
ERROR 1074 (42000): Column length too big for column 'name' (max = 255);
use BLOB or TEXT instead
```

### 1.3.2 VARCHAR：变长字符串

基本语法：

```sql
VARCHAR(L)
```

- 用于保存可变长度字符串。
- `L` 表示可存储的字符数。
- 最大长度与表的字符编码、行的其他字段以及长度记录开销有关。

示例：

```sql
CREATE TABLE IF NOT EXISTS t9 (
    id INT,
    name VARCHAR(6)
);
```

![[设置varchar数据.png]]

```sql
INSERT INTO t9 (id, name) VALUES (123, '张三');
INSERT INTO t9 (id, name) VALUES (123, '张三,hhhhh');
INSERT INTO t9 (id, name) VALUES (123, '张三,hhh');
```

第二条数据超过 6 个字符，插入失败；第三条刚好是 6 个字符，可以插入。

PDF 中的示例：

```sql
CREATE TABLE tt10 (
    id INT,
    name VARCHAR(6)
);

INSERT INTO tt10 VALUES(100, 'hello');
INSERT INTO tt10 VALUES(100, '我爱你，中国');
SELECT * FROM tt10;
```

```text
+------+--------------------+
| id   | name               |
+------+--------------------+
| 100  | hello              |
| 100  | 我爱你，中国       |
+------+--------------------+
2 rows in set (0.00 sec)
```

`VARCHAR` 的长度上限需要从字节角度理解：

- `VARCHAR` 最大可声明到 65535 字节附近。
- MySQL 还需要 1 到 3 个字节记录实际数据长度，因此有效数据空间约为 65532 字节。
- 实际一行还有表头、其他列等开销，所以 `VARCHAR(65535)` 并不总能创建成功。
- 如果表编码是 `utf8`，一个字符通常占 3 个字节，最大字符数约为 `65532 / 3 = 21844`。
- 如果表编码是 `gbk`，一个字符通常占 2 个字节，最大字符数约为 `65532 / 2 = 32766`。

验证 `utf8` 上限：

```sql
CREATE TABLE tt11 (
    name VARCHAR(21845)
) CHARSET=utf8;
```

```text
ERROR 1118 (42000): Row size too large. The maximum row size for the used
table type, not counting BLOBs, is 65535. You have to change some columns to
TEXT or BLOBs
```

降低到 21844 后可以创建：

```sql
CREATE TABLE tt11 (
    name VARCHAR(21844)
) CHARSET=utf8;
```

```text
Query OK, 0 rows affected (0.01 sec)
```

因此，原笔记中“最多 65536 字节、约 21845 个字符”的说法应修正为：声明上限与 65535 字节有关，扣除长度记录后约剩 65532 字节；使用 `utf8` 时，课堂示例中的最大字符数为 21844。

### 1.3.3 CHAR 与 VARCHAR 对比

| 对比项 | `CHAR` | `VARCHAR` |
| --- | --- | --- |
| 长度 | 固定长度 | 可变长度 |
| 空间 | 通常按声明长度预留，可能浪费 | 在不超过上限时按实际内容分配，更节省 |
| 效率 | 结构简单，通常更高 | 需要维护实际长度信息，通常更低 |
| 最大长度 | 最多 255 个字符 | 受 65535 字节、编码和整行长度限制 |
| 适用数据 | 长度完全相同的值 | 长度变化较大的值 |

### 1.3.4 选型建议

适合使用 `CHAR` 的数据：

- 身份证号。
- 手机号。
- 固定长度的 `MD5` 字符串。
- 其他长度基本固定、读取频繁的字段。

适合使用 `VARCHAR` 的数据：

- 姓名。
- 地址。
- 评论、描述和其他长度变化明显的内容。

选择原则：

- 数据长度固定或高度稳定时，优先 `CHAR`。
- 数据长度变化明显时，优先 `VARCHAR`，但必须保证最长数据能够存下。
- `CHAR` 的磁盘空间可能比较浪费，但定长结构的访问效率通常更高。
- `VARCHAR` 更节省空间，但需要额外的长度管理和变长处理成本。
- 定长的本质是提前开辟对应空间；变长的本质是在声明上限内“用多少，开辟多少”。

## 1.4 日期和时间类型

### 1.4.1 DATE

基本格式：

```text
YYYY-MM-DD
```

`DATE` 只保存日期，不保存具体时分秒，通常占用 3 个字节。

```sql
CREATE TABLE birthday (
    t1 DATE
);

INSERT INTO birthday(t1) VALUES('1997-7-1');
```

查询时会按标准格式显示：

```text
1997-07-01
```

### 1.4.2 DATETIME

基本格式：

```text
YYYY-MM-DD HH:MM:SS
```

- 同时保存日期和时间。
- 常用表示范围从 1000 年到 9999 年。
- 通常占用 8 个字节。

示例：

```sql
CREATE TABLE birthday (
    t1 DATE,
    t2 DATETIME,
    t3 TIMESTAMP
);

INSERT INTO birthday(t1, t2)
VALUES('1997-7-1', '2008-8-8 12:1:1');

SELECT * FROM birthday;
```

```text
+------------+---------------------+---------------------+
| t1         | t2                  | t3                  |
+------------+---------------------+---------------------+
| 1997-07-01 | 2008-08-08 12:01:01 | 2017-11-12 18:28:55 |
+------------+---------------------+---------------------+
1 row in set (0.00 sec)
```

即使输入时写作 `2008-8-8 12:1:1`，MySQL 也会按标准格式保存和显示为 `2008-08-08 12:01:01`。

### 1.4.3 TIMESTAMP

基本格式：

```text
YYYY-MM-DD HH:MM:SS
```

- `TIMESTAMP` 表示时间戳。
- 显示格式与 `DATETIME` 相同。
- 通常从 1970 年开始计算。
- 一般占用 4 个字节。
- 常用于记录一条数据的创建时间或最近更新时间。

在上面的插入示例中，只给 `DATE` 和 `DATETIME` 赋值，没有显式给 `TIMESTAMP` 赋值，但 `t3` 自动补上了当前时间：

```text
2017-11-12 18:28:55
```

### 1.4.4 自动填充与自动更新时间戳

继续更新前面的记录：

```sql
UPDATE birthday
SET t1 = '2000-1-1';

SELECT * FROM birthday;
```

更新后：

```text
+------------+---------------------+---------------------+
| t1         | t2                  | t3                  |
+------------+---------------------+---------------------+
| 2000-01-01 | 2008-08-08 12:01:01 | 2017-11-12 18:32:09 |
+------------+---------------------+---------------------+
1 row in set (0.00 sec)
```

可以看到：

- 插入数据时，`TIMESTAMP` 可以自动补上当前时间。
- 更新同一条数据时，`TIMESTAMP` 又会更新为当前时间。
- 这个特性适合论坛帖子、评论、订单状态等需要自动记录最后修改时间的场景。

课堂截图也验证了这一现象：

![[日期时间类自动更新时间戳.png]]

### 1.4.5 DATE、DATETIME 与 TIMESTAMP 对比

| 类型 | 保存内容 | 常见格式 | 常见占用空间 | 主要特点 |
| --- | --- | --- | --- | --- |
| `DATE` | 日期 | `YYYY-MM-DD` | 3 字节 | 不包含时间 |
| `DATETIME` | 日期和时间 | `YYYY-MM-DD HH:MM:SS` | 8 字节 | 范围大，表示完整日期时间 |
| `TIMESTAMP` | 时间戳 | `YYYY-MM-DD HH:MM:SS` | 4 字节 | 从 1970 年开始，可自动填充或更新时间 |

选择建议：

- 只需要记录生日、纪念日等日期时使用 `DATE`。
- 需要明确保存某一天的具体时间、且希望有更大年份范围时使用 `DATETIME`。
- 需要记录创建时间、最后更新时间并利用自动更新能力时使用 `TIMESTAMP`。

## 1.5 ENUM 和 SET 类型

### 1.5.1 ENUM：枚举与单选

基本语法：

```sql
ENUM('选项1', '选项2', '选项3', ...)
```

`ENUM` 是“单选”类型：

- 建表时提供若干固定选项。
- 一个单元格最终只保存其中一个值。
- 出于存储效率考虑，选项在内部以数字编号保存。
- 选项按声明顺序对应 `1、2、3、...`，最多可有 65535 个选项。
- 插入时既可以写选项文本，也可以写对应的数字编号。

例如：

```sql
ENUM('男', '女')
```

其中 `1` 对应“男”，`2` 对应“女”。

注意：课堂笔记中“下标从 0 开始”的说法应更正。MySQL 将第一个 `ENUM` 选项对应的编号设为 1，而不是 0。

### 1.5.2 SET：集合与多选

基本语法：

```sql
SET('选项值1', '选项值2', '选项值3', ...)
```

`SET` 是“多选”类型：

- 一个单元格可以保存多个已声明的选项。
- 多个选项使用逗号分隔来插入和显示。
- 内部用比特位表示，每个选项按顺序对应一个二进制位。
- 对应数值依次为 `1、2、4、8、16、32、...`。
- 最多可以声明 64 个选项。
- 集合语义下重复选项会被去重，同一个选项只需保存一次。

`SET` 的数字编码可以类比 Linux 文件权限中的比特位，因为二者都是通过不同二进制位表示多个状态。

### 1.5.3 表结构与示例

调查表需要记录用户的单选性别和多选爱好：

```sql
CREATE TABLE votes (
    username VARCHAR(30),
    hobby SET('登山', '游泳', '篮球', '武术'),
    gender ENUM('男', '女')
);
```

其中：

- `hobby` 是 `SET`，允许从“登山、游泳、篮球、武术”中多选。
- `gender` 是 `ENUM`，只允许“男、女”二选一。

课堂中的另一组选项：

![[创建枚举类型.png]]

```sql
CREATE TABLE IF NOT EXISTS votes (
    username VARCHAR(30),
    gender ENUM('男', '女'),
    hobby SET('代码', '羽毛球', '乒乓球', '篮球')
);

INSERT INTO votes
VALUES ('张飞', '男', '篮球');

SELECT * FROM votes;
```

```text
+----------+--------+--------+
| username | gender | hobby  |
+----------+--------+--------+
| 张飞     | 男     | 篮球   |
+----------+--------+--------+
1 row in set (0.00 sec)
```

### 1.5.4 插入与数字编号

可以按文本插入：

```sql
INSERT INTO votes
VALUES('雷锋', '登山,武术', '男');
```

也可以使用数字：

```sql
INSERT INTO votes
VALUES('Juse', '登山,武术', 2);
```

在 `ENUM('男', '女')` 中，数字 `2` 表示第二个选项“女”，因此查询：

```sql
SELECT * FROM votes
WHERE gender = 2;
```

可以得到：

```text
+----------+---------------+--------+
| username | hobby         | gender |
+----------+---------------+--------+
| Juse     | 登山,武术     | 女     |
+----------+---------------+--------+
1 row in set (0.00 sec)
```

虽然 MySQL 允许用数字表示 `ENUM` 和 `SET` 的值，但不建议在日常写入时这样做，因为数字不利于代码阅读，也不利于表结构维护。

### 1.5.5 查询 ENUM

`ENUM` 是单值字段，可以直接按选项文本比较：

```sql
SELECT *
FROM votes
WHERE gender = '男';
```

这条语句查找所有性别为“男”的记录。

### 1.5.6 查询 SET：FIND_IN_SET

假设表中有以下数据：

```text
+-----------+---------------+--------+
| username  | hobby         | gender |
+-----------+---------------+--------+
| 雷锋      | 登山,武术     | 男     |
| Juse      | 登山,武术     | 女     |
| LiLei     | 登山          | 男     |
| LiLei     | 篮球          | 男     |
| HanMeiMei | 游泳          | 女     |
+-----------+---------------+--------+
```

如果使用普通等值查询：

```sql
SELECT *
FROM votes
WHERE hobby = '登山';
```

只能查到 `hobby` 恰好等于 `'登山'` 的记录：

```text
+----------+--------+--------+
| username | hobby  | gender |
+----------+--------+--------+
| LiLei    | 登山   | 男     |
+----------+--------+--------+
1 row in set (0.00 sec)
```

它无法查出 `'登山,武术'` 这种包含“登山”的记录。

此时应使用 `FIND_IN_SET`：

```sql
FIND_IN_SET(sub, str_list)
```

- `sub` 是要查找的单个值。
- `str_list` 是用逗号分隔的字符串。
- 如果 `sub` 存在于 `str_list` 中，返回它的位置，从 1 开始。
- 如果不存在，返回 0。

基础示例：

```sql
SELECT FIND_IN_SET('a', 'a,b,c');
SELECT FIND_IN_SET('d', 'a,b,c');
```

结果分别为 `1` 和 `0`。

查询所有喜欢“登山”的人：

```sql
SELECT *
FROM votes
WHERE FIND_IN_SET('登山', hobby);
```

```text
+----------+---------------+--------+
| username | hobby         | gender |
+----------+---------------+--------+
| 雷锋     | 登山,武术     | 男     |
| Juse     | 登山,武术     | 女     |
| LiLei    | 登山          | 男     |
+----------+---------------+--------+
3 rows in set (0.00 sec)
```

这条查询既能匹配单独的“登山”，也能匹配 `SET` 中包含“登山”的多选项。

课堂截图示例：

![[使用find_set查询.png]]

需要注意：

- `FIND_IN_SET` 的第一个参数应该是单个选项，不应直接写成 `'篮球,代码'`。
- 如果要同时匹配多个选项，需要分别调用函数并用 `AND` 连接：

```sql
SELECT *
FROM votes
WHERE FIND_IN_SET('篮球', hobby)
  AND FIND_IN_SET('羽毛球', hobby);
```

这样才能查询“同时喜欢篮球和羽毛球”的记录。

### 1.5.7 NULL 与类型边界

- `NULL` 表示“什么都没有”，是真正未赋值或未知的空值。
- 没有写 `NULL` 不代表它自动等于空字符串；具体还要看列是否允许空、默认值是什么。
- `''` 是长度为 0 的字符串，与 `NULL` 的概念不同。
- 枚举、集合、字符串、数字和日期类型都有各自的合法边界。
- 超过类型允许范围的数据，可能直接报错、被拒绝，或在特定 SQL 模式下产生警告和转换，因此必须按实际边界设计字段。

## 1.6 总结

### 1.6.1 各类型核心记忆点

| 类型 | 核心记忆点 |
| --- | --- |
| `TINYINT` | 默认有符号，范围 -128 到 127；无符号范围 0 到 255 |
| `BIT` | 位字段，`BIT(M)` 的 `M` 为 1 到 64，默认 `BIT(1)` |
| `FLOAT` | 4 字节、近似浮点、精度约 7 位，精度敏感场景慎用 |
| `DECIMAL` | 定点数，精确控制总位数和小数位，适合金额等高精度数据 |
| `CHAR` | 定长，最多 255 个字符，长度按字符计算 |
| `VARCHAR` | 变长，受 65535 字节、编码和整行大小限制 |
| `DATE` | 只保存日期，通常 3 字节 |
| `DATETIME` | 保存完整日期时间，通常 8 字节 |
| `TIMESTAMP` | 时间戳，通常 4 字节，可自动填充和更新时间 |
| `ENUM` | 单选题，内部编号从 1 开始 |
| `SET` | 多选题，内部使用 `1、2、4、8、...` 的比特位编码 |

### 1.6.2 数据类型选择检查表

设计字段时依次检查：

1. 这个值表达的是数字、文本、日期、状态还是多选题？
2. 值的最大和最小范围是什么？
3. 长度是否固定？编码会如何影响空间？
4. 是否需要精确小数？
5. 是否需要自动创建或更新时间？
6. 是否允许 `NULL`？业务默认值是什么？
7. 数据增长后，当前类型是否仍然够用？

### 1.6.3 核心结论

数据类型既是对数据的分类，也是对数据的约束。合适的类型可以同时保证正确性、存储效率和查询语义；过度放大类型虽然看似安全，却可能浪费空间，也不能代替合理的业务约束。

> 数据类型的价值不只是“允许保存什么”，更在于“及时拒绝不该保存的内容”。

> 本部分是表约束内容的第一部分，整合 [[Codex Attachments/05-MySQL表的约束.pdf|05-MySQL表的约束.pdf]] 中 5.1 至 5.5 节与 [[2026-10-20 MySQL表的约束：上]] 中的课堂记录。截图与原始实验现象保留，语法、业务示例和结论统一整理。

## 2.1 从数据类型到表级约束

### 2.1.1 为什么只有数据类型还不够

数据类型首先约束“这一列能保存什么值”，例如 `TINYINT` 限制整数范围，`CHAR(2)` 限制字符数量。这种约束很重要，但它通常只检查单个值是否符合类型边界，无法完整表达业务规则。

例如，一个邮箱字段要求“不能为空且不能重复”，又或者班级字段要求“每个班级必须对应一个教室”。这些问题都不是单纯换一个数据类型就能解决的，需要额外的表级约束：

- `NOT NULL` 防止关键字段缺失。
- `DEFAULT` 为经常重复出现的值提供默认结果。
- `COMMENT` 为字段补充可维护、可阅读的说明。
- `ZEROFILL` 控制整数补零后的显示格式。
- `PRIMARY KEY` 保证记录能够被唯一、非空地标识。
- `AUTO_INCREMENT`、`UNIQUE KEY` 和 `FOREIGN KEY` 分别处理自动编号、业务唯一性与表间关联。

因此，表的约束并不是数据类型之外的可选装饰，而是把业务逻辑翻译成数据库能够主动执行和检查的规则。

### 2.1.2 约束要解决的问题

约束的最终目标是保证数据完整性、合法性和可预期性。它同时影响数据库和程序员：

- 从程序员角度看，约束会在写入前暴露错误，避免“代码以为写对了，数据却不符合业务”。
- 从 MySQL 角度看，进入表中的数据必须已经满足列定义和约束，后续查询才能建立在可靠的数据基础上。
- 从系统维护角度看，约束把一部分审核工作交给数据库，减少应用层遗漏检查造成的脏数据。

可以把数据类型与约束的关系概括为：

> 数据类型规定“一列允许保存什么”，表约束进一步规定“一条记录在业务上必须满足什么”。

### 2.1.3 本章约束一览

| 约束或属性 | 主要作用 | 典型问题 |
| --- | --- | --- |
| `NULL` / `NOT NULL` | 控制字段是否允许缺失 | 教室字段为空，无法判断上课地点 |
| `DEFAULT` | 未显式赋值时提供默认值 | 新用户年龄默认从 0 或 18 开始 |
| `COMMENT` | 保存字段说明，便于阅读和维护 | `age` 究竟表示周岁还是年龄等级 |
| `ZEROFILL` | 按声明宽度用 0 补齐显示 | 商品编号 `1` 显示为 `00001` |
| `PRIMARY KEY` | 非空且唯一地标识一行 | 两个学生拥有同一个学号 |
| `AUTO_INCREMENT` | 自动生成连续编号 | 每次插入都要手工寻找下一个编号 |
| `UNIQUE KEY` | 约束某列或列组合在业务上不重复 | 两个员工使用同一个员工工号 |
| `FOREIGN KEY` | 维护主表与从表之间的引用关系 | 学生引用了不存在的班级编号 |

本文先展开前五项，后三项在第二部分继续整理。

## 2.2 空属性

### 2.2.1 NULL 与 NOT NULL

字段的空属性主要有两个取值：

- `NULL`：字段允许为空，也是 MySQL 在没有其他限制时的常见默认状态。
- `NOT NULL`：字段必须拥有一个值，不允许写入 `NULL`，也不能在插入时遗漏该字段。

`NULL` 表示“没有值”或“值未知”，并不表示空字符串 `''`，也不表示数字 `0`。它还有一个关键特点：普通运算遇到 `NULL` 后，结果通常仍然是 `NULL`。

```sql
SELECT NULL;
SELECT 1 + NULL;
```

两个结果都是 `NULL`：

```text
+------+
| NULL |
+------+
| NULL |
+------+

+--------+
| 1+null |
+--------+
|   NULL |
+--------+
```

这就是实际开发中要尽量避免关键字段为空的直接原因：数据虽然成功存进来了，但后续统计、比较和计算可能都无法得到有效结果。

![[非空约束不允许为空.png]]

### 2.2.2 用业务规则决定是否允许为空

假设要创建班级表，表中包含班级名和教室名。按照正常业务逻辑：

- 班级没有名字，就无法识别这是哪一个班。
- 教室为空，就无法知道这个班在哪里上课。

因此，这两列都应该声明为 `NOT NULL`：

```sql
CREATE TABLE myclass (
    class_name VARCHAR(20) NOT NULL,
    class_room VARCHAR(10) NOT NULL
);
```

查看表结构：

```sql
DESC myclass;
```

```text
+------------+-------------+------+-----+---------+-------+
| Field      | Type        | Null | Key | Default | Extra |
+------------+-------------+------+-----+---------+-------+
| class_name | varchar(20) | NO   |     | NULL    |       |
| class_room | varchar(10) | NO   |     | NULL    |       |
+------------+-------------+------+-----+---------+-------+
```

`Null` 列中的 `NO` 表示该字段不允许为空。若只提供班级名而不提供教室名：

```sql
INSERT INTO myclass(class_name) VALUES('class1');
```

MySQL 会拒绝写入：

```text
ERROR 1364 (HY000): Field 'class_room' doesn't have a default value
```

这条错误同时揭示了空属性与默认值的联系：字段既不允许为空，又没有可用的默认值，插入时就不能省略它。

### 2.2.3 空属性的使用原则

- 姓名、学号、状态、数量等参与业务判断的关键字段，应根据业务要求优先设置为 `NOT NULL`。
- 确实可能“尚未填写”或“业务未知”的字段才允许 `NULL`，例如尚未分配的宿舍号。
- 不要把 `NULL` 当作空字符串或 0 的替代写法。
- 判断 `NULL` 应使用 `IS NULL` 或 `IS NOT NULL`，不能用 `= NULL` 得到预期的真假结果。
- `NOT NULL` 只保证字段有值，不能保证值一定正确；正确性还需要数据类型、唯一键或其他业务约束共同完成。

## 2.3 默认值

### 2.3.1 DEFAULT 的含义

某个数据如果经常重复出现，可以在建表时为字段声明默认值。插入数据时，如果用户没有显式提供该字段的值，MySQL 就使用默认值。

基本形式：

```sql
列名 数据类型 [NOT NULL] [DEFAULT 默认值]
```

例如：

```sql
CREATE TABLE tt10 (
    name VARCHAR(20) NOT NULL,
    age TINYINT UNSIGNED DEFAULT 0,
    sex CHAR(2) DEFAULT '男'
);
```

查看表结构：

```sql
DESC tt10;
```

```text
+-------+---------------------+------+-----+---------+-------+
| Field | Type                | Null | Key | Default | Extra |
+-------+---------------------+------+-----+---------+-------+
| name  | varchar(20)         | NO   |     | NULL    |       |
| age   | tinyint(3) unsigned | YES  |     | 0       |       |
| sex   | char(2)             | YES  |     | 男      |       |
+-------+---------------------+------+-----+---------+-------+
```

此时只插入姓名：

```sql
INSERT INTO tt10(name) VALUES('zhangsan');
SELECT * FROM tt10;
```

未指定的 `age` 和 `sex` 自动取得默认值：

```text
+----------+------+------+
| name     | age  | sex  |
+----------+------+------+
| zhangsan |    0 | 男   |
+----------+------+------+
```

![[设置默认值.png]]

### 2.3.2 DEFAULT 与 NOT NULL 的关系

`DEFAULT` 与 `NOT NULL` 并不冲突，它们分别回答两个不同问题：

- `NOT NULL` 回答“字段能不能没有值”。
- `DEFAULT` 回答“用户省略这个字段时，系统应该填入什么”。

二者组合后的行为是：

| 插入情况 | 允许 `NULL`，有默认值 | `NOT NULL`，有默认值 | `NOT NULL`，无默认值 |
| --- | --- | --- | --- |
| 显式写入合法值 | 成功 | 成功 | 成功 |
| 显式写入 `NULL` | 成功 | 失败 | 失败 |
| 省略字段 | 使用默认值 | 使用默认值 | 失败 |

因此，`name VARCHAR(20) NOT NULL DEFAULT ''` 这类定义是有意义的：它既禁止 `NULL`，又允许调用方省略字段并自动得到空字符串。默认值不能把“显式插入 `NULL`”变成默认值，它只在该字段根本没有出现在 `INSERT` 语句中时生效。

![[not null和default不冲突.png]]

### 2.3.3 省略字段时的边界

某些允许 `NULL` 的字段没有显式声明 `DEFAULT`，`DESC` 中仍会显示 `Default` 为 `NULL`。这表示省略字段时采用隐式空值；它不等于声明了业务上的非空默认值。

因此，“只有设置了 `DEFAULT` 的列才能省略”应理解为一种安全经验：对于 `NOT NULL` 且没有默认值的列，省略一定会失败；允许 `NULL` 的列虽然可能因隐式空值而插入成功，但得到的数据未必符合业务预期。

![[如果你不写，系统默认会添加default null.png]]

实际设计时建议：

- 对经常会省略、且有明确业务初值的字段声明 `DEFAULT`。
- 不能让核心字段悄悄变成 `NULL` 时，同时声明 `NOT NULL`。
- 不要为了“省事”给所有字段都设置空洞默认值；默认值应表达真实业务含义。

## 2.4 列描述

### 2.4.1 COMMENT 的用途

`COMMENT` 用来描述字段的业务含义。它不会参与数据校验，也不会改变字段类型或取值范围，但会随建表语句保存在数据字典中，方便程序员、DBA 和后续维护者理解表结构。

课堂示例：

```sql
CREATE TABLE IF NOT EXISTS t14 (
    name VARCHAR(20) NOT NULL COMMENT '这个是用户名',
    age TINYINT UNSIGNED DEFAULT 18 COMMENT '这个是用户的年龄',
    gender CHAR(1) DEFAULT '男' COMMENT '这个是用户的性别'
);
```

等价地，PDF 中还使用了更容易对应字段名称的注释：

```sql
CREATE TABLE tt12 (
    name VARCHAR(20) NOT NULL COMMENT '姓名',
    age TINYINT UNSIGNED DEFAULT 0 COMMENT '年龄',
    sex CHAR(2) DEFAULT '男' COMMENT '性别'
);
```

![[comment示例.png]]

### 2.4.2 如何查看 COMMENT

`DESC` 主要显示字段类型、是否允许空、键、默认值和额外属性，不显示注释：

```sql
DESC tt12;
```

```text
+-------+---------------------+------+-----+---------+-------+
| Field | Type                | Null | Key | Default | Extra |
+-------+---------------------+------+-----+---------+-------+
| name  | varchar(20)         | NO   |     | NULL    |       |
| age   | tinyint(3) unsigned | YES  |     | 0       |       |
| sex   | char(2)             | YES  |     | 男      |       |
+-------+---------------------+------+-----+---------+-------+
```

要查看注释，需要读取完整建表语句：

```sql
SHOW CREATE TABLE tt12\G
```

其中会保留：

```sql
`name` varchar(20) NOT NULL COMMENT '姓名',
`age` tinyint(3) unsigned DEFAULT '0' COMMENT '年龄',
`sex` char(2) DEFAULT '男' COMMENT '性别'
```

### 2.4.3 COMMENT 不是数据约束

`COMMENT` 只能帮助人理解字段，不能阻止错误数据。例如注释写了“年龄”，数据库并不理解年龄是否允许负数，也不会自动检查格式。真正的边界仍然需要类型、`NOT NULL`、`CHECK`、唯一键或外键等约束完成。

书写注释时，应说明字段的业务口径，而不是简单重复列名。例如，`unitprice` 的注释应说明“单价，单位分”，这比只写“商品单价”更有维护价值。

> 注意：`NOT NULL` 与 `DEFAULT` 是否同时出现，要看业务规则。`DEFAULT` 确有值时通常可以保证字段有合法默认值，但显式写入 `NULL` 仍需由 `NOT NULL` 拦截，所以二者并非简单互斥。

## 2.5 ZEROFILL

### 2.5.1 整数后面的数字是什么

早期 MySQL 中，整数类型后面可能显示长度，例如 `INT(10)`。这个数字并不是整数占用 10 字节，也不一定限制取值范围，而是与显示宽度有关。

先看 `tt3`：

```sql
SHOW CREATE TABLE tt3\G
```

```sql
`a` int(10) unsigned DEFAULT NULL,
`b` int(10) unsigned DEFAULT NULL
```

在没有使用 `ZEROFILL` 时，这个宽度通常只会影响展示，不能阻止更大的合法整数显示出来。

![[类型字段长度不写会默认添加.png]]

### 2.5.2 用 ZEROFILL 补零显示

`ZEROFILL` 是显示格式属性：当实际数字宽度不足声明宽度时，在左侧补 `0`。修改列：

```sql
ALTER TABLE tt3
CHANGE a a INT(5) UNSIGNED ZEROFILL;
```

原来的数据是 `a = 1`、`b = 2`，查询后 `a` 会显示为 `00001`：

```sql
SELECT * FROM tt3;
```

```text
+-------+------+
| a     | b    |
+-------+------+
| 00001 |    2 |
+-------+------+
```

![[添加zerofill.png]]

补零规则包括：

- 位数不足声明宽度时，在左侧补 `0`。
- 实际数字位数已经达到或超过声明宽度时，完整显示数字，不会截断。
- 补零只影响查询结果的格式化显示，不改变参与运算和比较的数值。
- 因此 `00001` 与数字 `1` 在数据意义上相同。

### 2.5.3 用 HEX 证明底层值没有变

可以通过十六进制函数观察实际值：

```sql
SELECT a, HEX(a) FROM tt3;
```

```text
+-------+--------+
| a     | hex(a) |
+-------+--------+
| 00001 | 1      |
+-------+--------+
```

显示为 `00001`，但内部保存和参与计算的仍然是 `1`。

`ZEROFILL` 改变的是“按什么格式展示”，不是“底层保存成什么数”。这也有助于区分显示宽度、实际字节宽度和符号位：无符号整数可以把原本的符号位用于表示更大的非负范围，而补零只是输出格式。

### 2.5.4 使用建议与版本差异

- `ZEROFILL` 适合旧系统中为了对齐编号而要求等宽显示的课堂场景。
- 新项目更建议在应用层格式化编号，避免把展示需求固化进存储结构。
- 整数显示宽度和 `ZEROFILL` 在较新的 MySQL 版本中已被弃用或弱化，实际行为应以目标版本文档为准。
- `ZEROFILL` 不提供唯一性、非空性或范围约束，不能替代 `UNIQUE KEY`、`NOT NULL` 等规则。

## 2.6 主键约束

### 2.6.1 主键的定义

主键使用 `PRIMARY KEY` 声明，用于非空且唯一地标识表中的一条记录：

- 主键字段不能重复。
- 主键字段不能为空。
- 一张表最多只能声明一个主键。
- 一个主键可以由一列构成，也可以由多列共同构成。
- 主键列通常是整数等相对稳定的类型，常见例子是学号或代理编号。

“表最多只有一个主键”并不等于“只能给一列加主键”。主键可以是单一字段，也可以是多个字段组合而成的复合主键。

### 2.6.2 创建单列主键

```sql
CREATE TABLE tt13 (
    id INT UNSIGNED PRIMARY KEY COMMENT '学号不能为空',
    name VARCHAR(20) NOT NULL
);
```

查看结构：

```sql
DESC tt13;
```

```text
+-------+------------------+------+-----+---------+-------+
| Field | Type             | Null | Key | Default | Extra |
+-------+------------------+------+-----+---------+-------+
| id    | int(10) unsigned | NO   | PRI | NULL    |       |
| name  | varchar(20)      | NO   |     | NULL    |       |
+-------+------------------+------+-----+---------+-------+
```

`Key` 列的 `PRI` 表示主键。即使建表时没有显式写 `NOT NULL`，主键也会自动带来非空要求。

![[主键的设置.png]]

![[MySQL对主键的描述.png]]

正常插入一条记录：

```sql
INSERT INTO tt13 VALUES(1, 'aaa');
```

再次插入相同主键：

```sql
INSERT INTO tt13 VALUES(1, 'aaa');
```

MySQL 会拒绝：

```text
ERROR 1062 (23000): Duplicate entry '1' for key 'PRIMARY'
```

主键的核心意义在于可寻址性：只要知道主键，就能确定至多一条记录，后续查询、更新、关联都可以围绕这个稳定标识展开。

### 2.6.3 添加和删除主键

如果建表时没有主键，之后可以追加，但现有数据必须满足非空且唯一：

```sql
ALTER TABLE test_key
ADD PRIMARY KEY(id);
```

删除主键：

```sql
ALTER TABLE test_key
DROP PRIMARY KEY;
```

使用时有两点需要特别注意：

1. 如果已有重复值或 `NULL`，追加主键会失败，必须先清理数据。
2. 不要等表运行一段时间后才补主键。越晚发现重复数据，修复成本和影响范围通常越大。

删除主键会取消“唯一且非空标识记录”的主键约束，但不会自动替你生成另一个主键。字段原本由主键带来的 `NOT NULL` 属性不一定会随主键一起消失，删除后应再执行 `DESC` 检查。删除前还应检查其他表是否依赖它，避免破坏后续的关联关系。

### 2.6.4 复合主键

多列共同构成一个主键时，称为复合主键。课堂示例可整理为：

```sql
CREATE TABLE pick_course (
    id INT UNSIGNED,
    course_id INT UNSIGNED COMMENT '课程编号',
    score TINYINT UNSIGNED COMMENT '这个学生课程考的分数',
    PRIMARY KEY (id, course_id)
);
```

PDF 中的另一种等价案例使用课程代码 `course`：

```sql
CREATE TABLE tt14 (
    id INT UNSIGNED,
    course CHAR(10) COMMENT '课程代码',
    score TINYINT UNSIGNED DEFAULT 60 COMMENT '成绩',
    PRIMARY KEY (id, course)
);
```

![[主键不在一列上.png]]

复合主键约束的是“整组字段的组合值”：

```sql
INSERT INTO pick_course VALUES(1, 101, 90);
INSERT INTO pick_course VALUES(1, 102, 85);
```

上面两条可以同时存在，因为 `(1, 101)` 与 `(1, 102)` 是不同的组合。若再次插入：

```sql
INSERT INTO pick_course VALUES(1, 101, 95);
```

则违反复合主键：

```text
ERROR 1062 (23000): Duplicate entry '1-101' for key 'PRIMARY'
```

课堂中的业务含义是：同一个学生不能重复选择同一门课程，但一个学生可以选择多门课程；同一门课程也可以被多个学生选择。单独看 `id` 或单独看 `course_id` 都可能重复，只有二者放在一起才能唯一标识一条选课记录。

### 2.6.5 主键设计建议

- 优先选择稳定、不会频繁变化的字段作为主键。
- 纯业务字段可能因政策或业务调整而改变时，可以考虑使用与业务无关的代理编号。
- 主键只用于标识一行，不应为了“顺便加很多限制”而把过多字段塞进复合主键。
- 非空且唯一是主键的最低要求，不代表任何非空唯一值都适合承担主键的业务角色。
- 设计关联表时，主键与可能被引用的唯一键要提前规划，否则后续添加外键会更麻烦。

## 2.7 第一部分小结

### 2.7.1 约束对照

| 约束 | 是否改变可写入值 | 是否影响显示 | 主要检查 |
| --- | --- | --- | --- |
| `NOT NULL` | 是，禁止空值 | 否 | 字段必须有值 |
| `DEFAULT` | 是，省略字段时补值 | 否 | 未赋值时采用的初值 |
| `COMMENT` | 否 | 否 | 仅保存说明 |
| `ZEROFILL` | 否 | 是，左侧补零 | 按声明宽度显示数字 |
| `PRIMARY KEY` | 是，禁止重复和空值 | `Key` 显示为 `PRI` | 非空且唯一地标识一行 |

### 2.7.2 核心结论

- 数据类型负责守住单值的基本边界，表约束负责表达更具体的业务规则。
- `NULL` 表示“没有值”或“未知”，会让普通运算结果继续变成 `NULL`。
- `DEFAULT` 只处理未显式赋值的字段，不能替代 `NOT NULL`。
- `COMMENT` 是可维护性工具，不是校验规则。
- `ZEROFILL` 只改变显示格式，不改变实际存储和数值语义。
- 主键必须非空且唯一，可以是单列或复合列；复合主键的唯一性作用于整组字段。
- 约束应在建表阶段尽量设计完整，不应等脏数据出现后再补救。

> 约束的价值在于把业务规则前置到数据入口：越早拒绝错误数据，后续查询、修改和关联的成本就越低。
